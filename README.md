# CheckStock

Прототип учёта товара на складах фулфилмента (ФФ).
Показывает, где находится товар: физически на складе,
в резерве FBS, в пути между ФФ, на складе маркетплейса (FBO)
или у клиента (FBS).

## Стек

- Python 3.12
- FastAPI + Uvicorn
- SQLAlchemy 2.0 (async) + asyncpg / aiosqlite
- Alembic (миграции)
- Jinja2 (шаблоны)
- Pydantic (валидация форм)

## Запуск

    python -m venv venv
    source venv/bin/activate  # Windows: venv\Scripts\activate
    pip install -r requirements.txt
    cp .env.example .env      # Windows: copy .env.example .env
    alembic upgrade head
    python seed.py
    uvicorn app.main:app --reload

Открыть: http://127.0.0.1:8000
Swagger: http://127.0.0.1:8000/docs

По умолчанию .env использует SQLite — ничего устанавливать не нужно.
Для PostgreSQL раскомментируйте строку в .env и укажите свои данные.

## Тестовые данные

После python seed.py создаются:

- Склады: Север, Юг
- Товары: SKU-101 Органайзер, SKU-102 Контейнер, SKU-103 Корзина
- Остатки: Север — 10/5/0, Юг — 6/0/4

## Сценарии проверки

### Приход

1. + Приход → SKU-102, Юг, 3 → Оформить приход.
2. У SKU-102 / Юг: физически 3, доступно 3, резерв 0.

### Резерв FBS

1. Резерв FBS → SKU-101, Север, 2 → Зарезервировать.
2. У SKU-101 / Север: физически 10, доступно 8, резерв 2.
3. В истории — FBS_RESERVE, статус «В ожидании», кнопки Отправить / Отменить.
4. Отправить → резерв 0, физически 10. Товар в блоке «В пути к клиенту (FBS)».
5. Доставлено → физически 8, блок опустеет.
   Отменить (до отправки) — вернёт к 10/0.

### Перемещение

1. Перемещение → SKU-101, Север → Юг, 2 → Отправить.
2. У Севера физически 8. В блоке «В пути между ФФ» — запись.
3. Принять → форма приёмки. Укажите факт 2 → Подтвердить.
4. У Юга физически 8 (было 6 + 2).

### Акт расхождения

1. Отправьте перемещение SKU-101, Север → Юг, 5.
2. Принять → укажите факт 3, комментарий «недостача».
3. У Юга физически +3 (не 5). В блоке «Акты расхождения» — запись 5 → 3, −2 (недостача).

### FBO

1. Отправка FBO → SKU-102, Север, 2 → Отправить.
2. У Севера физически 3. В блоке «В пути на маркетплейс» — запись.
3. Принять → блок опустеет, на ФФ ничего не зачисляется.

### Склады

1. Склады → создайте Тест, переименуйте, удалите (если пустой).
2. Попробуйте удалить Север с остатком — ошибка «На складе осталось N ед.».
3. Восстановите удалённый склад кнопкой Восстановить.

### Товары

1. Товары → создайте товар (только название) → артикул сгенерируется
   автоматически по шаблону `SKU-NNN`.
2. Переименуйте товар.
3. Удалите пустой товар — он станет «Удалён», в основной таблице пропадёт.
4. Восстановите его кнопкой «Восстановить».
5. Попробуйте удалить товар с остатком — ошибка «На складах осталось N ед.».

### Нехватка

1. Резерв FBS → SKU-103, Север, 10 (там 0).
2. Сообщение: «На складе Север доступно 0 шт., нужно 10. Есть на: Юг — 4 шт.».

## Ключевые решения

**Async-стек.** FastAPI + SQLAlchemy async (asyncpg / aiosqlite).
Это даёт неблокирующие запросы к БД и соответствует современному
подходу к FastAPI. Все роуты и сервисы — async def.

**SQLite по умолчанию, PostgreSQL — опция.** В .env — DATABASE_URL
для SQLite, чтобы запустить проект без установки
PostgreSQL. Модели и миграции совместимы с PostgreSQL: достаточно
поменять DATABASE_URL на postgresql+asyncpg://...

**Soft-delete складов.** Склад не удаляется физически, а получает
is_active = False. Это сохраняет остатки и историю (ТЗ: «При
удалении сохраните остатки и историю»). Блок «Где числится товар»
показывает все склады, включая архивные, с пометкой «(архив)».

**Запрет удаления склада с остатком или товаром в пути.** Если на
складе есть физический остаток, или с него/на него едет товар —
удаление блокируется с понятной ошибкой.

**Отдельные блоки «в пути».** По ТЗ товар в пути делится на три
категории: между ФФ, на маркетплейс (FBO), к клиенту (FBS). На
главной — отдельные блоки для между ФФ и FBO; FBS закрывается
отправкой.

**Валидация в два слоя.** Pydantic-схемы (app/schemas.py)
проверяют форму (типы, qty > 0). Бизнес-правила
(app/validators.py) — остаток, активность склада, статус операции.
Сервисы (app/services.py) только меняют состояние.

**Обработка ошибок.** ValueError из сервисов ловится в роутерах и
возвращается на ту же страницу с ?error=..., а не 500.
Пользователь видит понятное сообщение.

**Идемпотентность.** Повторное подтверждение операции (отправка,
приёмка, отмена) проверяет статус и не списывает товар дважды.

**Константы в одном месте.** Статусы, типы операций и русские метки
— в app/constants.py. Модели и шаблоны используют их.

**Остатки на FBO.** Отдельная модель `MarketplaceStock` — сколько
товара уехало на маркетплейс и было принято. При приёмке FBO
увеличивается на `qty`. В будущем — синхронизация через API
маркетплейса и валидация расхождений (TODO в коде).

## Ограничения

- Нет интеграции с реальным API маркетплейсов (Ozon, WB, ЯМ) — вне ТЗ.
  Остатки на складе маркетплейса (FBO) ведутся вручную: +qty при приёмке.
  В будущем — синхронизация через API и валидация расхождений.
- Нет аутентификации и прав доступа — однопользовательский прототип.
- FBS-отправка сразу закрывает операцию: отдельного блока «В пути к
  клиенту» нет, товар списывается.
- Нет тестов (pytest) — проверка ручная по сценариям выше.
